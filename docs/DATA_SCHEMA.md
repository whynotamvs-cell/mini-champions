# DATA_SCHEMA.md — данные игрока и DataStore

> Версия схемы: **1**
> Связано: `docs/ARCHITECTURE.md` (PlayerDataService), `docs/ECONOMY.md` (лимиты), `docs/TEST_PLAN.md` (раздел «Данные»).

## 1. Угрозы, от которых защищаемся

| # | Угроза | Как возникает | Защита |
|---|---|---|---|
| T1 | **Конфликт сессий** | Игрок быстро перезаходит на другой сервер, пока старый ещё не сохранил данные. Новый сервер загружает старую версию, затем старый сервер её перезаписывает — или наоборот | Блокировка сессии (session lock): профилем владеет ровно один сервер |
| T2 | **Дублирование наград** | Повторная отправка RemoteEvent, гонка двух обработчиков, повтор после ошибки | Серверная машина состояний забега + `grantId` + отсутствие `yield` между проверкой и записью |
| T3 | **Дублирование через откат** | Получил награду → сервер упал до сохранения → данные откатились, но игрок «помнит» покупку | Немедленное сохранение после важных событий; приемлемое окно потерь задокументировано |
| T4 | **Потеря прогресса при сбое DataStore** | Ошибки/лимиты DataStore при загрузке или сохранении | Повторы с экспоненциальной задержкой; при неудаче загрузки игрок не получает «пустой» профиль |
| T5 | **Порча данных** | Ошибка в коде записывает `nil`/`NaN`/отрицательное значение | Валидация перед сохранением, лимиты из ECONOMY.md, `Reconcile` с шаблоном |
| T6 | **Несовместимость версий** | Новая версия кода читает старые данные или наоборот | `SchemaVersion` + последовательные миграции; старый код не трогает данные новой схемы |
| T7 | **Смешивание тестовых и боевых данных** | Studio пишет в боевое хранилище | Отдельный тестовый experience + `ProfileStore.Mock` по умолчанию в Studio |

## 2. ProfileStore или собственная реализация

### Сравнение

| Критерий | ProfileStore | Собственная реализация |
|---|---|---|
| Session lock | Есть, проверен на крупных играх; использует `UpdateAsync` и MessagingService для быстрого освобождения блокировки на другом сервере | Нужно написать и протестировать самим: метка сессии в данных, таймаут «мёртвой» блокировки, освобождение при выходе |
| Автосохранение | Есть, с экспоненциальной задержкой при сбоях | Писать самим |
| Сохранение при остановке сервера (`BindToClose`) | Есть | Писать самим; легко ошибиться с таймаутом 30 с |
| Расход лимитов DataStore | Оптимизирован, задокументирован | Зависит от нас |
| Тестирование | Есть `ProfileStore.Mock` для Studio | Писать мок самим |
| Межсерверные сообщения профилю | Есть (`MessageAsync` / `MessageHandler`) | Писать самим |
| Прозрачность | Один ModuleScript, лицензия Apache-2.0, исходник можно прочитать | Полная |
| Зависимость | Внешний автор; обновления не под нашим контролем | Нет |
| Время на MVP | Часы | Дни + риск тонких багов |

### Рекомендация (решение D1)

**ProfileStore**, при этом:
1. Хранить закреплённую версию в репозитории (`src/server/Vendor/ProfileStore.luau`) с указанием версии и даты в комментарии. Обновлять сознательно, отдельным коммитом, с прогоном тестов данных.
2. **Изолировать за адаптером.** Весь остальной код знает только `PlayerDataService`; прямой `require` ProfileStore есть ровно в одном файле. Если когда-нибудь понадобится своя реализация, меняем один модуль.
3. Не использовать возможности ProfileStore, без которых можно обойтись в MVP (межсерверные сообщения — только после MVP).

Собственная реализация оправдана только при требованиях, которые ProfileStore не покрывает (например, особая модель шардирования). Для MVP таких требований нет.

> При интеграции сверить точные сигнатуры по актуальной документации ProfileStore (`StartSessionAsync`, `Reconcile`, `AddUserId`, `OnSessionEnd`, `EndSession`, `Save`, `ProfileStore.Mock`). Ниже — псевдокод, а не окончательный API.

## 3. Хранилища и ключи

| Параметр | Значение |
|---|---|
| Имя хранилища | `PlayerData_v1` |
| Ключ профиля | `Player_<UserId>` |
| `UserId` в метаданных | Да (`AddUserId`) — нужно для запросов на удаление данных по GDPR/правилам Roblox |
| Experience для разработки | Отдельный тестовый experience (решение D3); боевые ключи из Studio не трогаем |
| Studio по умолчанию | `ProfileStore.Mock` (ничего не пишется); реальный DataStore — только при флаге `Config.Studio.UseRealDataStore = true` в тестовом experience |

Суффикс `_v1` у хранилища меняется **только** при несовместимой смене всей модели хранения. Обычные изменения схемы делаются миграциями внутри того же хранилища.

## 4. Схема данных v1

```luau
export type PlayerDataV1 = {
	SchemaVersion: number, -- = 1

	-- Валюта и прогресс
	Stars: number,          -- 0..1_000_000, целое
	LifetimeStars: number,  -- сколько всего заработано (для аналитики и будущих достижений)
	XP: number,             -- общий опыт, целое ≥ 0; уровень вычисляется из XP

	-- Обучение
	Tutorial: {
		Step: number,        -- последний завершённый шаг, 0..5
		Completed: boolean,
	},

	-- Клуб
	Club: {
		UpgradesOwned: number, -- 0..8; улучшения покупаются по порядку, поэтому хватает счётчика
	},

	-- Мини-игры
	Minigames: {
		DeskDash: {
			Finishes: number,
			BestTimeMs: number,   -- 0 = рекорда нет
			Medals: {
				Bronze: boolean,
				Silver: boolean,
				Gold: boolean,
			},
		},
	},

	-- Идемпотентность наград (кольцевой буфер последних grantId)
	RecentGrants: { string }, -- не более 50 элементов

	-- Настройки игрока
	Settings: {
		MusicVolume: number,   -- 0..1
		SfxVolume: number,     -- 0..1
		Language: string,      -- "auto" | "en" | "ru"
		ReducedMotion: boolean,
	},

	-- Служебное
	Meta: {
		FirstJoinUnix: number,
		LastJoinUnix: number,
		SessionCount: number,
	},
}
```

### Шаблон (значения по умолчанию)

```luau
local TEMPLATE: PlayerDataV1 = {
	SchemaVersion = 1,
	Stars = 0,
	LifetimeStars = 0,
	XP = 0,
	Tutorial = { Step = 0, Completed = false },
	Club = { UpgradesOwned = 0 },
	Minigames = {
		DeskDash = {
			Finishes = 0,
			BestTimeMs = 0,
			Medals = { Bronze = false, Silver = false, Gold = false },
		},
	},
	RecentGrants = {},
	Settings = { MusicVolume = 0.6, SfxVolume = 0.8, Language = "auto", ReducedMotion = false },
	Meta = { FirstJoinUnix = 0, LastJoinUnix = 0, SessionCount = 0 },
}
```

### Почему так

- **Уровень игрока и уровень клуба не хранятся** — вычисляются из `XP` и `UpgradesOwned`. Меньше полей = меньше рассинхрона.
- **`UpgradesOwned` — счётчик, а не набор**, потому что покупка строго по порядку (ECONOMY.md). Если порядок станет свободным — миграция на набор ID.
- **Не храним** имя, отображаемое имя, страну, устройство, IP и любые личные данные. Только игровое состояние.
- **Не храним** состояние текущего забега, номер участка, текущих соседей — это данные сессии сервера.
- Размер профиля — сотни байт; лимиты размера ключа не грозят.

## 5. Жизненный цикл профиля

```text
PlayerAdded
  └─ StartSessionAsync("Player_<UserId>", { Cancel = игрок уже вышел? })
       ├─ nil (игрок вышел во время загрузки) → ничего не делаем
       ├─ nil (сбой DataStore после повторов) → Kick с локализованным сообщением
       │                                         "Не удалось загрузить прогресс, попробуй ещё раз"
       └─ profile
            ├─ AddUserId(UserId)
            ├─ Reconcile()                 — дополнить недостающие поля из шаблона
            ├─ Migrate(profile.Data)       — до текущей SchemaVersion
            ├─ Validate(profile.Data)      — зажать значения в допустимые диапазоны, залогировать аномалии
            ├─ OnSessionEnd → если игрок ещё в игре → Kick ("Сессия открыта на другом сервере")
            ├─ если игрок уже вышел → EndSession()
            └─ иначе → отметить профиль "Ready", обновить Meta, отправить клиенту снимок

PlayerRemoving
  └─ отменить активный забег (без награды) → EndSession()  — ProfileStore сохраняет и снимает блокировку

BindToClose
  └─ ProfileStore сам завершает сессии; мы только отменяем забеги и не начинаем новых операций
```

**Правило «Ready»:** пока профиль не загружен, игрок не может начать забег, купить улучшение или получить награду. Все серверные обработчики проверяют `PlayerDataService:IsReady(player)`.

## 6. Защита от дублирования наград (T2)

Три уровня:

### Уровень 1 — машина состояний забега (основной)

Забег существует только на сервере: `Countdown → Running → Finished → Rewarded` (или `Abandoned`). Награда выдаётся при переходе `Finished → Rewarded`. Переход происходит ровно один раз, потому что:
- проверка состояния и смена состояния выполняются **синхронно, без `yield`** между ними (Luau однопоточен в пределах одного актора, поэтому другой обработчик не вклинится);
- клиент вообще не присылает «я финишировал» — финиш фиксирует сервер по касанию серверной зоны финиша и проверке чекпоинтов.

### Уровень 2 — `grantId`

Каждая выдача имеет уникальный идентификатор:
- забег: `dash:<runId>` (`runId` = `HttpService:GenerateGUID(false)`, создаётся сервером при старте забега);
- разовые награды: детерминированный ID, например `tutorial:first_finish`, `medal:dash:gold`, `level:7`.

`RewardService:Grant(player, source, amount, grantId)`:
1. если `grantId` есть в `RecentGrants` → no-op, залогировать;
2. для разовых наград дополнительно проверить постоянный флаг (`Medals.Gold`, `Tutorial.Step`) — он и есть главная защита, `RecentGrants` — страховка;
3. проверить лимиты (сумма ≤ 500, баланс ≤ 1 000 000, источник из перечисления);
4. изменить `Stars`, `LifetimeStars`, флаги; добавить `grantId` в `RecentGrants` (выкинуть самый старый, если > 50);
5. залогировать экономическое событие.

Шаги 1–4 — без `yield`.

### Уровень 3 — покупки идемпотентны по смыслу

`ClubService:Purchase(player, upgradeIndex)` принимает **номер следующего улучшения**. Если `upgradeIndex ~= UpgradesOwned + 1` — отказ. Повторная отправка того же запроса после успешной покупки автоматически отклоняется, двойное списание невозможно.

## 7. Сохранение и окно потерь (T3, T4)

| Событие | Сохранение |
|---|---|
| Обычный ход игры | Автосохранение ProfileStore (интервал по умолчанию библиотеки) |
| Покупка улучшения | `profile:Save()` сразу (решение D4) |
| Первая медаль, завершение обучения | `profile:Save()` сразу |
| Обычная награда за забег | Автосохранение |
| Выход игрока | `EndSession()` |
| Остановка сервера | ProfileStore через `BindToClose` |

**Окно потерь:** при аварийном падении сервера теряется прогресс обычных забегов с момента последнего сохранения (до интервала автосохранения). Покупки и разовые награды не теряются. Для MVP это приемлемо и задокументировано; дублирования при этом не возникает, потому что откатываются **одновременно** и Stars, и то, на что они потрачены.

**Бюджет запросов DataStore:** немедленные сохранения бывают не чаще раза в ~1–2 минуты на игрока, что укладывается в лимиты при 6 игроках на сервере. Перед релизом сверить актуальные лимиты DataStore и хранилища в документации Roblox.

## 8. Миграции (T6)

```luau
-- src/server/Services/PlayerData/Migrations.luau
local MIGRATIONS = {
	-- [fromVersion] = function(data) ... return data end  -- приводит к fromVersion + 1
	-- [1] = function(data) data.Club.Decor = {}; data.SchemaVersion = 2; return data end,
}
```

Правила:
1. Миграции только вперёд, по одной версии за шаг, чистые функции, без `yield`.
2. Каждая миграция покрыта тестом: «данные версии N → ожидаемые данные версии N+1».
3. Если `data.SchemaVersion > CURRENT_VERSION` (сервер со старым кодом загрузил данные от нового) — **не изменять и не сохранять**: кикнуть игрока с сообщением «Обновление сервера, перезайди». Это защищает данные во время постепенного обновления серверов.
4. Удалять поля только после того, как миграция их перенесла, и не раньше чем через одно обновление.

## 9. Валидация (T5)

Перед каждым изменением и после загрузки:

| Поле | Правило |
|---|---|
| `Stars` | целое, 0..1 000 000; `NaN`/`inf` → откат операции + лог ошибки |
| `XP` | целое ≥ 0 |
| `Club.UpgradesOwned` | целое 0..8 |
| `Tutorial.Step` | целое 0..5 |
| `BestTimeMs` | 0 или ≥ `minValidTime` (35 000) |
| `Settings.*Volume` | 0..1 |
| `Settings.Language` | одно из `auto`, `en`, `ru` |
| `RecentGrants` | ≤ 50 строк, каждая ≤ 64 символов |

Значения вне диапазона после загрузки — зажимаются и логируются (`TelemetryService` + `warn`), а не приводят к сбросу профиля.

## 10. Восстановление

- DataStore хранит предыдущие версии ключей ограниченное время; ProfileStore предоставляет функции для чтения версий. Для MVP достаточно задокументированной ручной процедуры восстановления конкретного игрока из версии (скрипт в `tools/`, запускается вручную в тестовом/боевом experience владельцем). Точный срок хранения версий сверить в документации.
- Удаление данных по запросу (право на удаление): процедура удаления ключа `Player_<UserId>` вручную; описать в `docs/RELEASE_CHECKLIST.md` до релиза.
